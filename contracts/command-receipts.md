# 设备命令回执确认与安全回收

本合同扩展已有设备通信和原命令账本，不增加第二套命令状态机。当前消费者为 Rust 网关与 TV Agent；没有协商本扩展的原生 MCU、模拟器和适配器保持原协议。设备日志与应用安装版本分别演进，当前验证范围见 [实施进度](../docs/24-实施计划与进度.md)。

## 有序且与 ID 绑定的命令

网关新建命令使用 `c1-<sequence>-<uuid>` 作为 command_id，并令下行 message_id 与其相同。sequence 是原账本的持久受理序号，十进制无前导零，范围1至9007199254740991；uuid 为小写标准连字符形式。HTTP、CLI及用户客户端继续将完整 ID 视为不透明字符串。设备上行 seq 是另一种报文序号，不能用作本边界。

序号在受理时与命令同事务保存，从原账本最大值递增；失败/取消/过期也不复用原序号。当前网关保留全部原命令，最多4096条，未实现其归档；未来回收网关记录须另保留耐久序号分配依据，不能删记录使最大值倒退。恢复校验拒绝序号越界、重复正序号，以及 c1 ID、message_id、原命令 ID和保存序号不一致；旧快照的缺省序号0不作为新命令序号。

## 协商与重连边界

设备在 hello.body 声明 `receipt_ledger: 1`。网关只向声明者在原 welcome.body 增加 `receipt_ledger: 1` 和 `command_sequence`，后者为当前原命令账本的最大受理序号；没有命令时为0。不识别的版本拒绝，未声明的设备不收到额外字段或下行确认。

TV Agent 要求明确协商成功。welcome 仍须匹配本次挑战、身份、模型与连接；网关 head 小于本机 high_watermark 时拒绝本会话，报告 gateway_history_rollback。head 较大时先耐久更新本机 high_watermark，再上报 ready；新会话之前的命令均不能再次执行。这也使设备单边旧备份能从保留完整账本的原网关恢复拒绝边界。

收到新命令时，设备要求两个 ID 相同且符合上述格式，sequence 严格大于本机 high_watermark；原命令与新边界在副作用前同一次提交。保留记录内的精确完整原包重投仍只返回原结果，异参拒绝；已回收 ID 的原包、异参或新会话重包均不能越过边界。消息乱序不会触发补执行。

同时恢复网关与设备的旧备份，或遗失两端全部历史，不能由这两个旧副本证明真实执行边界。该情况需要独立恢复依据或重新核对，不能通过调大序号、清库、换身份或自动重新受理旧用户请求宣称无损恢复。本扩展不提供同时回退两端的检测保证。

## 确认消息

网关收到并验证当前设备的 result 后，只有 confirmed/failed 的原结果已随账本和事件提交成功，才发布 `down/receipt`。消息沿用当前 Envelope、设备、模型与 session_id；body 严格包含：

```json
{
  "command_id": "c1-1-00000000-0000-4000-8000-000000000001",
  "command_digest": "sha256:<原完整下行Envelope的JCS摘要>",
  "result_digest": "sha256:<原result正文的JCS摘要>"
}
```

以上摘要为占位说明；实际格式是 sha256: 加64个小写十六进制字符。确认不表示物理效果超出原证据，submitted 仍只证明输入提交。unknown 和 result=null 不产生可回收确认。

设备在当前会话核对两个摘要、原命令和本机最终结果后，才耐久移除该条完整记录，保留 high_watermark。错误摘要、旧会话和试图确认未知记录均拒绝；重复确认已移除记录不再写盘。提交失败可能已生效，当前对象冻结，重开读取实际日志，不继续使用旧内存。

## 丢确认、重启与原结果核对

设备最多每两秒发送一条 `up/receipt`，沿用本次会话及新的上行 seq。body 严格包含 `command`（原完整下行 Envelope）与 `result`（本机原结果正文）。这是核对原结果，不是动作请求，不调用应用端口。

网关核对当前设备授权/会话、原命令账本归属、原执行路径为原生设备、完整 Envelope 摘要和原结果证据；随后按原命令自身保存的 session 核对结果。它可以收敛重启后 unknown 的原结果，但不能为已拒绝/未发送的命令制造执行证据。确认同样在原结果事务成功后发布；当前会话内合法的新包装允许重复核对。

完整且合法的up/receipt也明确声明当前会话使用本扩展，可恢复网关重启后丢失的会话内存标记；设备无需仅为此断开Broker。普通设备未使用此消息时不改变其握手或结果路径，核对失败也不启用回执标记。

旧会话下行确认失效，设备通过新会话重新查询；不自动重发原动作。设备只查询待确认的 confirmed/failed 记录；未知记录继续保留。网关结果、设备退休边界和 MQTT PUBACK 分别处理，不将传输确认当作账本确认。

## 设备日志与容量

设备应用启动配置日志v2、遥控组合配置日志v3保存空间/设备/当前模型、entries和high_watermark；v3允许保留旧应用模型的完整原Envelope，查询/确认仍核对该原包与结果，不改写历史模型或会话。最多128条/1MiB限制仍适用于尚未回收的记录；成功与拒绝在获得确认前也占容量。容量不足继续拒绝新动作，不淘汰unknown、未决或未确认结果。

应用配置只读加载并验证旧v1，首次实际提交写v2；切换到遥控配置须在hello前耐久迁为v3，Android在材料确认事务中原子迁移。日志格式、模型归属和单向迁移由 [设备合同](tv-agent.md) 维护，拒绝从v3退回旧模型。旧不透明ID的原最终结果可通过完整原包核对后回收，后续入站新命令必须使用有序ID，不能重新接纳已删除的旧ID。未知旧记录始终保留。新日志的边界须覆盖全部已保存的有序命令；损坏/未知版本拒绝且不改原字节。旧程序不能理解日志时须停止控制，不清数据降级。

此机制不延长命令有效期、不授予安装权限、不实现 Agent/ADB 混合路由，也不提供物理 exactly-once。身份撤销、APK更新及数据恢复继续遵循各自合同。

## 音频配置的命令日志v4

> 本节的未接线范围记录4.65冻结快照，当前本机授权见[本次运行授权](tv-agent.md#本次运行音频授权与电视端接线)；命令结果语义保持。

新音频应用/音频遥控配置复用本合同的原命令序号、耐久意图、submitted结果、unknown保留和摘要回收，不增加自动重发。两种新配置写v4，原应用/遥控配置继续写v2/v3；v4以当前模型精确修订区分，历史Envelope分别按原固定模型验证，不能借迁移把旧模型改为音频能力。仅允许增加能力的单向迁移，原包、结果、未决和high_watermark保持，旧程序遇v4拒绝。SQLite版本及APK更新账本版本均独立保持。

实际快照来自独立音频读取，命令最终结果只证明submitted。完整迁移矩阵及当前运行门禁见[tv-agent合同](tv-agent.md#音频精确模型命令与完整状态)；软件结果见[4.65](../docs/24-实施计划与进度.md#465-音频精确模型命令日志与完整状态)。本机授权、实际MQTT音频旅程与网页尚未接通，未访问电视。
