# 异构协议与适配器规范

更新日期：2026-11-02。状态：设计基线。平台保证核心语义独立，型号支持以 [30](30-设备支持矩阵与证据台账.md) 为准。

## 1. Port 与 Adapter

核心 Port 使用平台自己的设备引用、能力、观测、命令和错误。适配器负责发现、配对、能力描述、观测订阅、执行、健康检查与关闭；未支持的操作显式返回能力缺失，不要求每种协议假装支持相同生命周期。

| 接口职责 | 输入/输出 | 不变量 |
| --- | --- | --- |
| 发现 | 有期限扫描 → 候选及证据 | 候选不是已认领设备 |
| 配对/移除 | 当前授权、物理证明 → 绑定结果 | 不能无限开放入网 |
| 描述 | 精确型号/版本 → 能力子集及限制 | 不复制虚构能力 |
| 观测 | 原始帧 → 类型化观测/事件 | 保留来源、质量、时间 |
| 执行 | 已校验命令 → 发送阶段与后续结果 | 发送与完成分开 |
| 健康 | 连接、重启、资源、错误 | 辅助进程在线不等于设备在线 |

第三方 DTO、异常、厂商数据点和协议地址只在适配器内出现；核心错误稳定映射，必要原始证据以受控引用存放。

## 2. Zigbee

第一版固定一类 NCP 与固件，优先验证 CC2652/ZNP；主机侧 Rust 实现串口帧、请求关联、入网、访谈、ZDO/ZCL 能力映射、重连和设备 quirks。后续新增其他 NCP 驱动时复用核心 Port。

映射至少绑定 manufacturer/model、端点、Cluster、属性/命令、硬件/固件限制和映射修订。电池休眠、绑定/上报配置、重入网和网络备份分别验证；短地址变化不能创建重复设备。

网络密钥和协调器备份是敏感制品。未验证恢复时禁止宣称更换协调器可无损迁移。NCP 中的厂商 Zigbee 栈仍为外部依赖。

## 3. BLE

Linux 默认经 BlueZ D-Bus 适配；扫描和连接使用独立配额。广播传感器优先，只在实测支持时开展 GATT 控制和通知。

区分设备地址、隐私地址和逻辑设备身份。加密广播需当前用户提供或设备授权获取的密钥，无法解密时明确不可用；RSSI 不是可靠距离，更不是可信身份。

断连重订阅、通知丢失、MTU、配对状态和连接上限在型号档案中记录。协议要求的绑定密钥由密钥存储接口提供，不进入模型或公共证据。

## 4. 433

433 是频段称呼，适配需要明确频率、调制、脉冲编码、设备码和帧结构。接收、发送、双向反馈分别登记能力，不能由接收到遥控器推断可以可靠控制配对设备。

单向发送返回 `sent_only` 证据，设备实际状态通常为 estimated/unknown；没有确认通道时不能标 confirmed。滚动码、重放保护或缺少密钥的协议不承诺通用兼容。

接收器、收发器和 SDR 用途分开。rtl_433 可作为独立实验工具或符合许可的可选进程，不能将其实现无声明复制进核心。

## 5. Matter

分三项交付：Controller 认领并操作 Matter 设备；Bridge 将本平台设备暴露给其他 Matter 生态；Thread Border Router 提供 Thread IP 连通性。支持其中一项不能宣称三项全部实现。

标准栈在隔离模块或进程运行，以有版本的 IPC 合同连接。保存 Fabric、凭据与本地设备映射，验证 commissioning、订阅恢复、移除、共享及 Fabric 撤销。型号能力映射到核心物模型；不以 Matter Cluster 直接替代核心接口。

Matter SDK 可用不等于已获认证或商标使用资格，正式套件声明需有对应型号与认证依据。

## 6. 进程、权限与兼容

重依赖、FFI 或第三方运行时优先独立进程；IPC 限制消息大小、版本、权限和期限。平台管理生命周期、重启预算和健康状态，不给适配进程任意数据库、空间密钥或宿主 Shell 权限。

适配器发布带支持矩阵、模型修订、映射修订、依赖版本、许可证和证据引用。升级后重新访谈或重映射必须可预览，不静默改变属性单位与命令含义。

## 7. 合同验收

同一套假设备合同验证所有适配器：发现不授信、非法命令拒绝、重复结果去重、超时保留未知、退出释放资源、重启不串设备、背压有界。协议专项再以真实设备验证，对未执行项保持明确缺口。

## 8. Android TV 与存量电视

平台提供统一电视能力，Agent 承担获准的公开系统 API，ADB 或厂商接口由网关电视适配器实现。适配器集中处理发现、物理授权绑定、能力路由、执行、回读和健康，不将任意 Shell 或厂商 DTO 暴露到核心与客户端。

Agent和适配器共用一个逻辑设备，按动作固定唯一执行端；结果未知不自动切换路径。适配观测使用内部来源，不伪装原生MQTT身份；输入提交与实际界面变化按证据区分。当前 `bindings.bind` 保持完整动作集交给一个候选，`bindings.compose` 显式分区原生路径与一个外部候选，要求相同模型、当前原生会话及能力覆盖，FIFO跨端成立，详见 [执行合同](../contracts/execution-routes.md)。组合已有协议夹具/假ADB软件证据，TV Agent受控模型与日志迁移已有实现，真实JVM组合旅程仍未通过。两种内置配置不构成通用插件模型加载器，也不是第二类实际协议或插件宿主证据，不能越过第10.1节门槛。电视设计见 [34](34-电视终端与AndroidTV接入.md)，当前阶段见 [24 第4.15节](24-实施计划与进度.md#415-tv-agent模型配置与日志迁移文档同步)，型号支持只在 [30](30-设备支持矩阵与证据台账.md) 登记。

## 9. 多品牌扩展的粒度

采用协议适配器、型号档案/映射与必要 quirks 的组合，不默认“每个型号一个插件”。同一 Zigbee、BLE、Modbus 或获准厂商接口适配器可覆盖多个品牌；同品牌协议不一致时也可有多个适配器。这里的示例不表示相应协议已实现。型号识别保留精确指纹、固件/硬件范围及证据，无法唯一匹配时只提供已证实的最小能力。

| 扩展位置 | 解决的问题 | 交付与边界 |
| --- | --- | --- |
| 原生 SDK/BSP 组件 | 自有设备的芯片、驱动、资源和业务能力 | 编译进对应目标固件，随该硬件路径验证；不等于运行时插件 |
| 协议/厂商适配器 | 发现、配对、会话、协议读写与观测 | 第一方模块或受控独立进程，遵循核心 Port |
| 型号档案与声明式映射 | 型号指纹、单位、枚举、端点及版本差异 | 以不可变修订固定来源和测试；优先数据映射 |
| quirks 扩展 | 无法用简单映射表达的实际协议差异 | 作为代码审核与隔离；脚本与表达式不自动构成安全沙盒 |
| 升级提供方 | 指定目标的检查、传输、安装、查询及恢复 | 与控制能力独立声明，可共用连接；约束见 [13](13-OTA与制品交付规范.md) |
| UI 扩展 | 标准能力控件以外的专用交互 | 通过已有授权用例操作设备，不获得协议凭据或额外控制权 |

一般设备按模型生成控制界面；UI 扩展不包含唯一的设备控制逻辑。米家的扩展程序主要是 UI 机制，不能据此合并上述职责。组件/能力与型号的领域关系见 [04](04-领域模型与数据设计.md)，调研依据见 [35](35-多品牌设备接入与升级架构调研.md)。

### 9.1 接入路线选择

先按设备可修改范围、实际接口和所需能力选择路线，再确定适配器；品牌名称不决定接入方式。同一设备的控制、观测与更新可分别使用不同的获准绑定。

| 设备条件 | 优先路线 | 必须保留的限制 |
| --- | --- | --- |
| 自有硬件、可维护固件 | 原生 SDK 与产品驱动，按目标系统构建 | 资源、硬件保护、身份及升级机制逐目标验证 |
| 可安装应用的 Android/Linux 设备 | 独立设备 Agent 与公开系统 API | 按系统版本和实际权限声明能力；安装应用不增加系统权限 |
| 已有标准或获准本地接口 | 协议适配器 + 型号档案/映射 | 只暴露已核实能力，不要求刷机或安装 Agent |
| 仅有获准厂商云接口 | 云接入适配器 | 明示云依赖、地区/账号条件、限流和失联行为，不能承诺离线控制 |
| 仅有单向控制或广播 | 受限发送或观测适配器 | 分别登记可发送、可观察及无法确认的状态 |
| 无可用接口、目标无法唯一识别或用途未核实 | 保留候选与研究记录 | 不发布控制或升级支持；需要分析具体制品时按 [20](20-AI辅助逆向与设备适配流程.md) 取证 |

型号差异先用声明式映射表达，只有存在不可表达的真实协议差异时才增加 quirks 代码。新增协议不自动新增 UI 插件，新增型号不默认新增进程；更新能力由独立提供方声明。

## 10. 插件运行与发布约束

先在现有模块化网关中实现窄接口，第一方简单适配使用静态模块；重依赖、FFI、第三方代码或不同语言运行时优先使用可单独重启的进程。跨进程采用有版本、可校验、有大小和时限上限的 IPC。当前不建设稳定的 Rust 动态库 ABI，不把任意 `.so` 加载到核心作为通用插件方案，也不先建设插件市场、任意代码热加载或通用脚本运行平台。

进程分离本身不等于权限隔离。宿主按部署能力限制用户身份、文件目录、串口/USB、网络目的地、CPU/内存及消息配额；权限无法落实时必须明确标识部署限制。凭据由最小范围引用提供，不开放核心数据库和整个空间密钥，不因安装插件授予所有设备控制权。

每份适配发布至少固定：插件 ID 与版本、制品摘要、核心/IPC 兼容范围、目标 OS/架构、依赖锁及许可、请求权限、配置 Schema、支持型号/固件范围、模型/映射修订、维护者和证据。此为发布设计要求，尚不是正式 manifest Schema；发布版本与本地接入配置实例分开，一个发布可运行多个获准实例。

生命周期依次包含校验配置、准备资源、连接、描述/订阅、运行、退避重连、排空与停止。核心限制重启频率和背压；崩溃只使对应绑定降级，不重放历史命令。进程健康、协议会话健康、设备在线与能力可用分别报告。发现、配对、控制、升级及网络访问分项声明权限，不支持的生命周期操作显式拒绝。

更新时预览受影响设备、能力与规则，固定新版本和映射修订，再排空旧实例并切换，避免两个实例同时执行同一路径。重启后核对原命令结果；不确定的发送保持 unknown。制品回退必须核对配置/持久状态格式，不能保证降版本后仍能读取新版状态；密钥和当前撤销记录也不得随旧备份复活。

先以原生 MQTT 和电视适配验证共同边界，再用第二类协议样本验证复用后固化 IPC。新协议实现和正式插件合同分别经过合同与实机验收；本规范没有将当前 MQTT runtime 宣称为已实现的通用插件宿主。

### 10.1 提炼通用插件合同的门槛

先用真实差异确定扩展位置：只有指纹、单位、枚举和端点不同的，增加型号映射；同一协议存在无法声明式表达的差异时增加受控 quirks；会话、认证或传输机制不同才评估新增适配器。新增安装或恢复机制由升级提供方承接，界面差异由 UI 扩展承接，不能用一个插件接口统一承担这些职责。

通用 IPC 与 manifest 成为正式合同前，应有以下证据：

1. 第二类实际协议验证了与电视不同的连接、观测或端点行为，能区分共同语义和协议特例；不以第二个同协议型号代替。
2. 两种接入均复用核心设备、授权、绑定与命令账本，合同夹具覆盖进程退出、期限、背压、旧结果和未知操作恢复，不依赖访问核心数据库。
3. 至少一个实际进程部署验证权限限制、版本协商、排空切换和配置/状态兼容；只能进程分离但尚未落实的权限约束如实登记。

满足门槛后再固定必要字段和兼容政策，扩展接口保持按职责拆分；原生固件组件、协议扩展、型号映射和升级提供方继续分别发布。当前阶段与后续工作包见 [24 第4.8节](24-实施计划与进度.md#48-文档复核与后续交付门槛)。

## 11. 唯一执行交接与恢复

第一方动作路由及现有空间的明确绑定/撤销已按[执行合同](../contracts/execution-routes.md)接通，复用命令账本与耐久提交；受限ADB的静态路由及现有空间接入均以假进程完成软件验证，实机另验。以下约束同时适用于后续扩展；通用 IPC、宿主配置热加载与跨执行端切换仍是设计目标，不在适配器中另建命令状态机。

1. 接受命令时固定逻辑设备、能力、模型/映射修订、绑定与唯一执行端；当前授权和执行意图先耐久提交。发送前重新核对期限、授权、绑定修订、能力和设备会话；检查失败拒绝发送，不自动改选另一端。
2. 在可能产生外部副作用前耐久标记尝试；提交失败为零发送。若标记已提交但进程中断，无法证明实际发送时保持 unknown，不能据此自动重试按键。原操作查询与新动作分开。
3. 调度只交给所选执行端；MQTT 发布与外部适配器执行不得各取同一命令。连接健康按绑定判断，Broker 离线仅影响依赖该 Broker 的路径，不能成为所有本地接口的共同开关。
4. 结果绑定原命令、执行端、输入及映射修订，保留实际来源；应用退出码、协议送达和设备效果分别表达。适配器结果经内部入口校验，不伪造原生设备 MQTT 身份。
5. 路由切换或适配器更新先停止旧路径接收新任务，核对在途操作，再启用新路径；旧路径的迟到证据仍关联原操作。对未知操作仅查询或人工核对，不以新实例、新通道或新幂等键补发。

合同测试至少覆盖两个执行端的发送计数、耐久提交失败、标记后中断、回执丢失、路由修订变化、撤权、适配器重启和旧结果迟到；模拟通过后再按 [23](23-测试策略与验收矩阵.md) 与 [30](30-设备支持矩阵与证据台账.md) 记录实机证据。

### 11.1 绑定与模型变更的验收约束

绑定、模型换绑和恢复必须检查同一组执行条件：路径及输入范围确实有实现，输出Schema与执行端证据相容，completion不超过其证明能力。仅有同名动作或submitted不足以判定兼容。当前外部入口只生成submitted与严格空输出；核心统一校验，ADB另按参考模型核对语义、risk、idempotent及输入子集。bind要求完整动作集；compose要求原生/外部完整分区，只给明确选择的路径执行权，不能把残缺旧绑定解释为组合。组合仍限仅动作模型，不支持属性/事件、多个外部候选或自动故障切换；恢复、输入边界和并发变更分别验收。

现有空间的绑定流程为：宿主准备候选 → 查询目标、模型/配置修订及应用授权 → 所有者明确批准 → 以预期绑定/模型修订校验并耐久提交 → 清除旧会话并重新探测。配置在重启时读取，完整config摘要变化使旧路径休眠，不自动接管；候选compatible不证明设备在线或授权完成。换绑拒绝OTA占用和dispatched在途；撤销可以立即阻断，并将可能已发送的操作保留unknown。旧探测不得复活新绑定，已有未知操作不经新路径补发。

撤销记录及每次变更的generation持久保存，阻止旧基线和MQTT回退；旧键只返回原决定，不重新激活历史绑定。应用GET只读当前绑定的15秒缓存，发现与配置授权分别呈现。首次启动的核心routes仍保留兼容，但不能改已有库的配置摘要或删库绕过。源码入口、已有空间完整软件旅程与实机缺口统一见 [24 第4.7节](24-实施计划与进度.md#47-适配绑定完整性与已有空间软件验收)，操作与配置详情仅由执行合同及适配器说明维护。
