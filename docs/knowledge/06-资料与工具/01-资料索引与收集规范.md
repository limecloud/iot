# 资料怎样收集、归类和核对

类型：资料组织方法与来源索引。目的：让知识库既能按顺序学习，也能在有具体问题时找到可靠材料。

## 1. 借鉴专业知识库的组织方式

所参考的 ima“减震设计助手”截图展示了：编号一级目录、高频问题入口、主题下的多级子目录，以及 Markdown、PDF、Word、图片和公众号文章等资料类型。可见的“法规政策 → 地方层面 → 区域 → 省市”体现了按适用范围继续细分的做法。

本次分析范围是截图中的可见结构，未核验库内全文和问答质量。迁移到 IoT 时，采用以下组织原则：

| 从截图中借鉴的方法 | 在本知识库怎样使用 |
| --- | --- |
| 高频问题单独放在前面 | 用十问定位“芯片、网关、智能、时延和成本” |
| 一级按专业主题分类 | 入门、标准生态、架构方法、场景、成本可靠性、资料工具 |
| 主题下再按适用范围细分 | 标准资料看协议与版本，设备资料看品牌、型号与固件 |
| 混合资料类型集中整理 | 保留官方原文入口，另写易懂摘要和适用边界 |
| 文件名可识别主题与时间 | 资料条目记录版本和观察日期；教程保持稳定名称 |

目录不必一次建到很多层。只有同类资料确实增多时，再增加协议、品牌或产品子目录，避免大量空文件夹。

## 3. 每条资料至少记录八件事

1. **问题与分类：** 这条资料解决什么问题，属于哪个主题。
2. **来源：** 标题、发布方、原始链接；实际打开了原文还是只看见目录。
3. **时间与版本：** 发布或更新日期、观察日期、协议或产品版本。
4. **适用范围：** 型号、固件、地区、网络和使用前提。
5. **原文明示的事实：** 短句摘录或准确转述，保留定位信息。
6. **自己的理解：** 为什么与当前问题有关，哪些只是类比或推断。
7. **未确认项：** 缺少哪些资料，下一次怎样核对。
8. **验证记录：** 是否有实验、条件、结果与限制；没有实验就写未做。

可以直接复制[资料收集模板](资料收集模板.md)填写。多篇文章需要同一份原始资料时，链接同一条来源记录，避免全文重复维护。

## 4. 怎样判断资料支持多大的结论

| 手里有什么 | 可以怎样表述 |
| --- | --- |
| 官网目录或搜索卡片 | “看到了这个品类或型号” |
| 实际读到的参数页或说明书 | “该版本资料明确写了这些参数与条件” |
| 工程设计文档 | “系统计划或约定这样工作” |
| 仿真或假提供方结果 | “这些合同与故障行为在模拟条件下成立” |
| 指定型号的真实测试 | “在记录的硬件、固件与条件下通过这些项目” |

不从“资料已收录”直接跳到“设备已支持”。不能从单个样本、品牌名称或带有“AI”的宣传语推导全部功能。

## 5. 以后优先补哪些资料

先围绕一个可验证场景补齐缺口。例如语音玩具：固定音频格式和硬件后，补终端驱动与缓冲资料、模型服务实际合同、弱网与取消行为、每分钟用量和真实时延记录。

标准原文与开发资料优先追溯到官方来源和具体版本。文章、视频和社区讨论可作为解释线索，再对关键参数核对原文。需要全文留存时，明确来源与可保存范围；有稳定原文链接时，先记录链接与摘要。
