# Linux 界面与工艺主控

当产品依赖成熟浏览器、复杂媒体、特定软件包或更大规模的本地处理时，可以评估 Linux 应用处理器与独立工艺 MCU 的组合。彩色触屏、中文输入或姓名排版本身并不足以证明必须使用 Linux。本章是备选路线分析，没有选定芯片和部署镜像。

## 分工与资源

Linux 侧运行产品界面、内容处理和业务连接；工艺 MCU 校验任务并执行实时控制。应用处理器通常需要配套 RAM、启动存储、电源管理、显示与触摸支持，BOM、启动时间、系统更新和长期维护均纳入总成本。

GUI 可按实际需求选择原生图形框架或浏览器界面，不能默认两者同时配齐。是否需要 GPU、视频解码或 NPU，由画面、媒体和算法目标及实测决定，不由“Linux”名称决定。

## 增量交付责任

| 项目 | 放行依据 |
| --- | --- |
| 板级与显示 | 对应处理器与板卡的系统支持、显示触摸驱动、存储寿命、电源及热设计验证 |
| 开机与可用性 | 启动、断电文件系统恢复、界面崩溃重启和离线行为达到产品阈值 |
| 更新与维护 | 镜像、启动链、更新失败与回退、漏洞响应、依赖和许可、维护期限有明确责任 |
| 工艺通信 | 复用双侧任务协议原则，验证重启、失联、重复和版本不兼容，工艺结果由本地主控记录 |
| 整机验证 | 在最终屏幕、结构、电源和软件组合上验证热、长时间稳定性、EMC/ESD及工艺质量 |

通用 Linux 的界面进程不应未经时限和故障分析就直接承担关键工艺输出；实时 Linux 或其他合并控制路线需要专门论证，不在本组展开。采用双处理器方案也仍需验证共同电源和链路故障。

openvela 官方说明其具备与 Linux/Android 的跨系统通信能力。[S16] 这不等于目标板已经具备可交付的混合系统，也不是同时部署这些系统的理由。
