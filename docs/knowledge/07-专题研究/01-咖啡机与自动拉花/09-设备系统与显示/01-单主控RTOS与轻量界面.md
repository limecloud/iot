# 单主控 RTOS 与轻量界面

一颗 MCU 可以同时管理设备界面和工艺任务。openvela/NuttX 加上经过适配的图形组件是一种候选组合；其他 RTOS 或成熟厂商 SDK 也可能满足需求。以下是工程路线分析，不是某款咖啡机已有实现。

## 系统分工

同一主控中分别运行传感采集、工艺控制、界面、通信和维护任务，通过受控的数据或消息交换协作。界面提交配方或打印任务，由工艺模块验证后执行；绘图代码不直接绕过工艺状态机操作加热和运动输出。

同芯片的任务划分不是物理故障隔离。内存破坏、长时间关中断、驱动阻塞或资源耗尽仍可能影响整个系统；线程优先级本身无法消除这些问题。必要的独立保护、互锁和故障安全策略按整机风险设计。

## 适用条件与板级工作

- 目标板已有可用 BSP，或团队有明确的移植、驱动验证和维护交付能力。支持某个 CPU 架构不等于目标芯片、板卡和外设已经适配。
- 根据实际界面计算和测量 CPU、RAM、Flash、显示带宽、任务栈和联网资源，不照搬“最小系统”宣传值。
- 为中文字体、输入法词库、模板和更新镜像安排存储；是否使用外部 Flash/PSRAM 等取决于芯片、驱动、带宽和可靠性验证。
- 固定硬件版本、系统发布版本、图形库及配置。S16 建议生产使用发布 tag，不能将开发分支页面直接当作量产软件基线。

## 放行证据

| 验证项 | 需要记录的结果 |
| --- | --- |
| 控制时限 | 最大界面刷新、连续触摸、图像解码、网络重连和日志压力下的控制任务执行时间与最坏延迟 |
| 资源余量 | 最坏输入和长时间运行下的内存峰值、线程栈、分配失败及恢复行为 |
| 交互质量 | 首屏、触摸响应、输入法候选、罕见字符提示、预览一致性，按产品确定的阈值判定 |
| 故障与恢复 | 界面异常、通信失败、看门狗、掉电和更新失败下的输出状态与恢复流程 |
| 批次一致性 | 固件、资源、校准数据和板卡版本可追溯，产线完成对应测试 |

当上述负载和故障边界难以满足产品要求时，评估[独立屏控路线](02-独立屏控与工艺主控.md)。无需仅因“想要屏幕”就增加第二颗处理器。
