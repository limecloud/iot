# 接口协议与系统边界

售货机协议涉及外设通信、设备数据、业务订单和支付通道等不同层。能够读取销售记录，不等于能够远程选货；具有 MQTT 或串口，不等于已经形成可靠交易系统。[V02、V11]

## 按责任分层比较

| 层次 | 典型接口或协议 | 主要用途 | 实施前必须核实 |
| --- | --- | --- | --- |
| 板内与机构 | GPIO、PWM、传感总线、厂商驱动协议 | 采集与输出 | 电气、时序、保护、状态反馈与硬件版本 |
| 售货外设 | MDB/ICP、设备厂商协议等 | VMC 与支付等外设的交互 | 主从角色、版本、功能级别、货币/金额语义、支持的交易模式 |
| 审计与数据交换 | DEX、VDI 等相关标准与数据格式 | 销售、审计或系统间数据交换，按对应标准确定 | 具体版本、字段和时点，是否允许读取/写入及是否包含所需事件 |
| 设备联网 | MQTT、HTTPS、厂商设备 SDK | 状态、告警和受限业务任务 | 身份、权限、有效期、重复/错序、结果确认和断线恢复 |
| 交易服务 | 订单、支付、退款、账单 API | 资金与业务状态 | 商户、密钥、验签、业务字段、幂等与资金对账 |

NAMA 页面分别列出 MDB v4.3 和服务器间 DEX 等标准。[V11] 本次只审阅标准目录，没有读取标准全文。EVA-DTS 的具体版本、传输方式和字段保留为实施前查证项，不在此编造字段映射。

## MDB 适配的实际含义

Qibixx 的 Cashless Master API 描述 VMC 一侧与无现金终端的通信，包含授权先行和选品先行模式、请求、完成、撤销及状态。正文还说明某些模式能否生效取决于对端支持，部分行为取决于固件版本。[V02]

因此，接入前应确定设备扮演 VMC、支付外设、旁路遥测还是其他角色。不能假设插上一个转接器就能控制所有货道，也不能把该厂商文本 API 当成 MDB 标准原始报文。

MDB 的电气层与普通开发板串口不是可以按名字直接互接的关系。应根据双方官方电气资料使用适配接口、供电和保护；本专题没有审阅其电气规范，不给出接线参数。

## 厂商整机 API 与封闭生态

采购时区分订单下发、货道控制、库存读取、故障事件、远程停售、重启与维护等具体能力。索要对应版本的文档、测试环境、权限模型、错误语义、费用、限流、升级兼容及终止服务后的数据/设备处置约定。

厂商自带运营后台可能已经覆盖交易与补货，新增平台应有明确收益。公开产品页、演示屏或串口插座都不足以证明开放集成权利和可交付接口。

## 可靠任务的最小语义

参考设计至少明确订单与任务标识、设备身份与生命周期、商品/货位及配置版本、数量、有效期、受限授权、执行状态与观测证据。状态机应区分接收、执行、完成、拒绝、失败和未知；同一标识异参请求需拒绝或按明确规则处理。

这些是设计要求，不是 LimeIoT 或某厂商当前已实现的接口合同。协议适配先证明语义正确，再测试真实机器的正常和异常路径，见[平台关联](09-与LimeIoT的关联判断.md)。
