# 屏幕、系统、算力与交互

售货机可以采用按键、小屏、彩色触屏或手机入口。常规交付控制不要求电脑级处理器和独立 GPU；界面、识别算法和协议负载决定额外算力。Vela/openvela 是候选系统基础之一，不是自动售货功能包。

## 软件与硬件分工

MCU 本身包含 CPU，适合按实际负载承担机构控制、传感采集和状态机。带屏方案还需显示/触摸驱动、图形组件、字体、资源存储和产品应用。复杂视觉识别可能需要独立计算模组，也可以选择不依赖视觉的交付方式。

| 产品形态 | 候选实现 | 主要验证内容 |
| --- | --- | --- |
| 按键或简单状态屏 | MCU 配按键和显示组件，采用合适固件/RTOS | 价格与货位对应、输入去抖、故障和取货提示 |
| 轻量触摸界面 | 适配过的 MCU/SoC、RTOS 与图形库 | CPU/RAM/Flash、刷新、字体、触摸与控制时限 |
| 独立 HMI 模组 | 模组运行界面，VMC 处理交付 | 图像/文本能力、协议、版本、重启和供应商维护 |
| 较复杂的业务屏 | Linux/Android 等应用处理器与工艺控制器按需组合 | 依赖、启动、存储、电源热设计、更新与故障边界 |
| 视觉自取柜 | 图像采集、识别、门控、交易与异常服务组成专门系统 | 模型和商品库、遮挡、拿放事件、争议处理与算力成本 |

这些不是指定 BOM。对 Vela/openvela、中文输入和显存计算的已查证原理，复用[系统与显示专题](../01-咖啡机与自动拉花/09-设备系统与显示/README.md)。支持某个架构不等于具体板卡已适配；带触屏也不等于必须同时运行 Linux 或大模型。

## 顾客使用流程

商品界面应显示价格、可售状态、必要商品信息和付款方式。订单创建后显示对应支付入口与超时；支付确认、设备准备、交付进度、取货和异常分别反馈。不要只显示无法解释的旋转等待动画。

没有本机大屏时，可由手机网页完成选择与付款，但需要可靠关联设备、点位、订单及顾客当前会话。二维码只是入口，不会自动完成身份认证、金额核验或出货授权。

定制场景可让顾客选择礼品组合、输入祝福语或姓名、预览并确认。软件可配置的字段与需更改机构/食品工艺的功能分开；“可输入任意文字”不代表机器能现场制造任意形状或完成真实倒奶写字。

## 多角色与交付现场

| 角色 | 需要的能力 | 边界 |
| --- | --- | --- |
| 顾客 | 选品、付款、取货、查询及联系客服 | 不能访问库存修改、任意开门和调试接口 |
| 补货员 | 核对点位、批次、货位、数量与保质信息 | 权限、维护模式与顾客交易隔离 |
| 维修员 | 诊断、受限动作测试、版本及故障记录 | 测试出货不冒充销售；维修后恢复需验收 |
| 运营人员 | 商品价格、点位、任务、售后与运营报表 | 变更可追溯，不能以报表覆盖物理库存 |

弱视、轮椅可达、触摸误操作、支付后离开、取货超时和多位顾客同时使用都应进入设计与点位测试。具体要求按产品和地区确定，不从屏幕尺寸单独推断可访问性合格。

## 量产配置

将屏幕模组、触摸固件、字体/模板、界面程序、VMC 固件、业务协议和支付组件纳入兼容矩阵。资源完整性、升级失败、断电、换板及长期供货都需验证。显示动画完成不能作为交付完成的证据。

产品案例见 V08 的现制饮品界面和 V09 的自取柜流程；来源见[台账](12-资料来源与证据边界.md)。
