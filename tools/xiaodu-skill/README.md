# 小度技能接入实验

通过小度官方自定义技能，将百度识别后的文字发送给指定的 OpenAI 兼容服务，再由小度播报回答。音箱唤醒、语音识别和语音合成仍由百度提供；本工具没有替换固件，也没有接管全局语音后端。当前适配器仅处理对话，尚未连接 LimeIoT 正式设备控制服务。

## 启动与验证

按 `config.example.json` 准备本机私有配置，填入官方技能 applicationId、提供方地址、模型和密钥。配置文件在 macOS/Linux 必须仅当前用户可访问，不能提交到仓库。

```sh
node "tools/xiaodu-skill/cli.mjs" "<私有配置文件路径>"
node --test "tests/xiaodu-skill.test.mjs" "tests/xiaodu-provider.test.mjs"
```

服务仅监听回环地址。官方 Web Service 地址应为经授权建立的 HTTPS 反向代理地址，路径为 `/dueros`。本工具不主动调用百度技能数据或通知 API，官方服务配置中选“不回调”，无需上传回调公钥。

示例配置启用 `deferredReplies`。模型未在 1.8 秒内完成时，先返回“正在思考”，保留当前会话的后台任务；用户稍后说“继续”取回结果，不会再次调用模型。“切回小度”会取消后台任务并清除待取结果。模型超时上限为 20 秒；超时或失败也通过后续“继续”返回明确提示。未取回上个回答时，新的问题会得到取答提示，避免静默丢弃问题或回答错位。

- `GET /healthz`：健康检查。
- `HEAD /dueros`：部署地址探活。
- `POST /dueros`：接收百度签名请求；无有效签名返回 401。

生产入口始终检查签名、证书来源/身份/有效期、applicationId 和时间戳。支持官方平台实际发送的 `v2.0` 以及文档中的 `2.0`，支持包含中间证书的 PEM 文件。日志只记录链路状态及受白名单约束的公开证书 URL，不记录用户原话、身份、签名或上游密钥。

## 验收范围

2026-11-02 的验证结果：

- 20 项针对性测试通过，覆盖多轮隔离、退出取消、去重、防重放、来源检查、续答取回及提供方错误处理。
- 指定模型曾独立返回“青柠助手连接正常”；后续两次对话请求超过 18 秒。一次流式请求成功返回“青柠对话已接通”，总耗时约 15.5 秒，延迟稳定性待验证。
- 临时 HTTPS 隧道的健康检查和探活通过，无签名请求被拒绝。
- 官方模拟器签名请求已到达本机，通过校验；百度实际返回欢迎语的 `Speak` 指令及继续聆听的 `Listen` 指令。退出请求返回结束语的 `Speak` 指令，不再包含 `Listen`。
- 网页模拟器存在已定位的显示异常：公开发布的前端对 `debug.bot.response_header` 调用 `JSON.parse`，实际字段是以 `Connection: close` 开头的 HTTP 响应头文本。异常中断了后续显示，所以欢迎语未显示、Response 面板为 null，不能据此断言服务未响应。已通过任务标签的被动网络观测核对真实返回指令，没有修改网页或绕过验签。
- 一次模型请求在平台端约 4.1 秒即返回 `3503 Request timed out`；因此单纯提高本地 10 秒超时不能解决同步回答问题。平台“技能内异步推送”已提交申请，当前状态为“审核中”，尚未启用异步发送。
- 已开启本技能的控制台真机调试开关。音箱仍须使用相同百度账号，并在设备端开启技能调试模式。
- 续答模式已用百度真实签名请求验证：提问返回等待提示，后续“继续”取回指定模型生成的“青柠对话已接通”，百度生成 `Speak` 和 `Listen` 指令，没有平台超时错误。此项是平台协议验证，尚不代表真机实际发声已确认。
- 多轮记忆通过平台协议验证：告知模型“测试编号是青柠七号”，取回“记住了”，再追问测试编号，取回“青柠七号”。过程中出现一次到 Cloudflare 临时地址的连接超时，重试取答成功；临时隧道稳定性仍有限。
- 尚未完成真机进入技能、AI 回答、多轮对话和退出回原厂服务的验收。
- 未运行项目整体构建；以上仅为独立实验工具的检查结果。

调用名称现为“柠檬管家”。因用户反馈“青柠助手”易被听错，已在平台更名，并补上传项目现有图标以修复平台的空 iconUrl 保存校验。服务端暂保留旧名称的文本识别兼容；这不代表平台仍可用旧名称唤起。

真机验证顺序：进入调试技能模式后，先说“小度小度”，等音箱应答后再说“打开柠檬管家”，确认欢迎语；提出一个简单问题，如听到等待提示，稍后说“继续”获取模型回答；说“切回小度”或“退出”，再测试原厂服务。若音箱已经停止聆听，可能需要重新唤醒；会话能否跨较长静默时间保留仍须真机验证。必须分别核对设备实际回应和服务日志。

## 系统与固件路线

目前已实测 DLNA 播放和音量控制，但这不能取得音箱麦克风。局域网仅发现 49494 和协议未知的 21608 端口，没有发现开放的 ADB 服务。设备只有圆形 DC 电源接口，准确硬件型号尚未确认。

因此尚无已验证的机内接管、固件刷写或双后端切换方案。若继续此路线，需要先确认硬件和可用的系统/调试入口，并形成可恢复的具体方案；不能凭端口响应推断存在 root、OTA 或麦克风接口。
